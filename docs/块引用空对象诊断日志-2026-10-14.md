## 现场证据与边界

`YJST-20261014.09580400.log` 记录模型空间中句柄 `D5` 的 `AcDbBlockReference`，实体索引 `72`，图层 `A-综合-建筑综合三`。读取 `vla-get-Name` 返回 `Automation 错误。 空对象 ID`，程序在扫描与生成计划阶段停止，尚未执行字体写入。

随后提供的 `YJST-20261014.10391700.log`、`YJST-20261014.10414900.log`、`YJST-20261014.10451000.log` 均没有新增诊断标识或事件；截图显示执行 YJST 后又打印旧版加载提示。工具集入口会重新加载自带 LSP，这几份日志没有提供对象与定义关联的新证据。

独立 v1 探测文件加载时会自动执行 DXF 读取、对象重新获取及 ActiveX 属性复探。用户反馈加载后 CAD 闪退。当前未取得崩溃前的 `YJST-D5-*.log`，不能确定具体触发调用，也不能仅凭原先空对象 ID 认定整个 DWG 损坏。

原实现还在整个诊断过程中保持日志流打开，进程退出可能使最后的缓冲记录丢失。读取操作与写入操作都可能进入原生接口，源码回归通过不能证明实际对象访问稳定。[Autodesk 的 ActiveX 错误处理说明](https://help.autodesk.com/cloudhelp/2026/ENU/AutoCAD-AutoLISP/files/GUID-9A862CD4-8CD8-4A03-8B65-0B08BD9BAE4F.htm)介绍的是拦截方法返回的异常；不能将这类异常捕获当成防止进程崩溃的保证。

## 当前主工具诊断

当前本地功能版本为 `0.2.13`，诊断标识为 `2026-10-14-font-verify-v5`，加载提示和 `RUN_BEGIN` 均显示。不可读块过滤在 v0.2.11 加入，v0.2.12 修复表格内容枚举，v0.2.13 继续保留并调整字体核验规则。公开 Release 和 CADTools 安装包尚未更新。

在读取块引用 Name 前先通过句柄读取实体 DXF。句柄解析或 DXF 明确返回 nil 时记录 `BLOCKREF_SKIPPED`，原因分别为 `HANDLE_NOT_RESOLVED` 或 `ENTGET_RETURNED_NIL`，该对象计入未覆盖，其他有效对象继续处理。未知接口异常仍保留原始报错并停止写入，不恢复、删除或修改异常对象。按句柄去重，重复不可读对象仅报告一次。

块名称读取失败后，只额外执行 `handent` 和 `entget`，记录原始错误、块/实体索引、解析状态及 DXF 身份字段。不再重复读取 Name、EffectiveName、ObjectID 等属性，不重新创建 ActiveX 对象，不遍历所属记录与块定义。

| 事件 | 内容 |
| --- | --- |
| `BLOCKREF_SKIPPED` | 句柄、类型、上下文、实体索引及空结果原因；停止后续 ActiveX 访问 |
| `BLOCKREF_DIAG_BEGIN` | 原始错误、句柄、类型、扫描上下文与 `DXF_ONLY` 模式 |
| `BLOCKREF_DIAG_PROBE_BEGIN` / `BLOCKREF_DIAG_PROBE` | 句柄解析前的检查点及返回状态 |
| `BLOCKREF_DIAG_DXF_BEGIN` / `BLOCKREF_DIAG_DXF` | DXF 读取前的检查点、错误或身份字段摘要 |
| `BLOCKREF_DIAG_IDENTITY` | 是否找到句柄、DXF 是否可读、DXF 句柄与块名 |
| `BLOCKREF_DIAG_END` / `BLOCKREF_DIAG_ERROR` | 诊断完成或自身异常；原始业务错误保持不变 |

上述原生读取开始与结束立即写入并关闭日志。正常块引用不执行异常探测。

每次原生读取前，`CALL_BEGIN` 先写入并关闭文件。返回后记录 `CALL_END` 或 `CALL_ERROR`；DXF 摘要保留组码 `0/2/5/8/66/67/70/100/102/330/340/350/360/410`，不展开几何和文字内容，也不打印实体指针。如果日志检查点无法落盘，停止继续读取目标对象。

## 11:28 现场日志与 nil 修复

`YJST-D5-DXF-20261014.11283400.log` 带有 v2 标识，记录 `handent` 成功返回 ENAME。`entget` 调用开始后出现 `DIAGNOSTIC_ERROR`：`参数类型错误: symbolp nil`，随后写出 `RUN_END`，状态为诊断中断。

定位到日志包装 `(vl-symbol-name (type result))`。原生 AutoLISP 对 nil 的 type 结果仍为 nil，传给 vl-symbol-name 会报上述错误；结合这条调用路径，可推断 entget 返回了 nil，而不是返回正常 DXF 列表。v3 将此结果明确记录为 `status=nil / valueType=NIL`，DXF 记录携带 `entgetStatus`，结束状态区分 DXF 已读取、DXF 不可读、句柄未找到和日志失败。

此前测试解释器将 `(type nil)` 错误地模拟为 SYM，并允许 vl-symbol-name 接受任意值，掩盖了问题。本次改成 type nil 返回 nil、vl-symbol-name 校验符号参数。修改后的解释器成功复现现场中断，再验证 v3 的两条空返回路径和既有运行/日志回归。

句柄可解析、DXF 不可读为已删除或无效实体提供线索，但不能仅据此确定对象损坏。[Autodesk handent 文档](https://help.autodesk.com/cloudhelp/2024/PLK/AutoCAD-LT-AutoLISP-Reference/files/GUID-AF6DD533-1A24-4687-96EB-F03F26050C07.htm)明确说明 handent 也可能返回当前编辑会话中已删除实体；[type 文档](https://help.autodesk.com/cloudhelp/2022/ENU/AutoCAD-MAC-AutoLISP-Reference/files/GUID-506C9CC8-B0BD-4A4C-B4C2-006750504509.htm)明确给出 type nil 返回 nil。

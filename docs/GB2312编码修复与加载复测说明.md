## 3 DeepSeek 必须落实的改动

1. 保留仓库根目录 `one-click-simsun.lsp` 为 UTF-8 开发源码；Markdown 文档及测试数据同样保留 UTF-8。
2. 建立可重复执行的转换工具，生成独立文件 `output/gb2312/one-click-simsun.lsp`，不能覆盖 UTF-8 源码。
3. 源文件先严格按 UTF-8 解码；可去除 UTF-8 BOM。目标严格按 `gb2312` 编码，写入的交付文件不带 BOM。
4. 对无法编码的字符明确报错，定位源文件、行、列及字符。禁止 `errors="ignore"`、`errors="replace"` 或默认问号替换；不可编码的注释或提示字符逐项改为可表示的写法，业务字符串须保留原语义。
5. 对交付文件执行严格 GB2312 解码、文本一致性和字节读回校验。编辑器显示为“ANSI”或“GBK”不能代替严格 GB2312 校验。
6. 每次修改源码后重新构建交付文件，记录源码路径、交付路径、构建时间及交付文件 SHA-256，确认复测加载的是本次文件。
7. 如果新增辅助 `.lsp`、启动器或 `.dcl`，将所有实际加载文件纳入同一构建及校验流程，避免入口为 GB2312、依赖仍为 UTF-8。
8. 更新使用说明，让用户只加载 GB2312 交付文件。程序不修改 `LISPSYS`、`SECURELOAD` 等系统设置。

GB2312 与 UTF-8 都可能包含完全相同的 ASCII 字节，因此“另存为后文件变小”或“没有 UTF-8 BOM”不能单独证明转换正确。以构建时采用的严格编码和完整读回结果为准。

## 4 可直接采用的转换工具

将以下代码保存为仓库内的 `tools/build_gb2312.py`，文件本身使用 UTF-8。在仓库根目录执行：

```powershell
python -X utf8 tools/build_gb2312.py
```

示例针对首版单文件插件；如果后续存在辅助加载文件，扩展文件清单并逐个执行同样的严格校验。

```python
from datetime import datetime
from hashlib import sha256
from pathlib import Path


def main():
    source = Path("one-click-simsun.lsp")
    target = Path("output/gb2312/one-click-simsun.lsp")

    try:
        raw = source.read_bytes()
        text = raw.decode("utf-8-sig", errors="strict")
    except (OSError, UnicodeDecodeError) as exc:
        print(f"SOURCE_ERROR: {source.resolve()}: {exc}")
        return 1

    try:
        payload = text.encode("gb2312", errors="strict")
    except UnicodeEncodeError as exc:
        line = text.count("\n", 0, exc.start) + 1
        column = exc.start - text.rfind("\n", 0, exc.start)
        bad = text[exc.start:exc.end]
        print(f"ENCODING_ERROR: {source.resolve()}:{line}:{column}: {bad!r}")
        return 1

    if payload.decode("gb2312", errors="strict") != text:
        raise RuntimeError("GB2312 round-trip mismatch")

    target.parent.mkdir(parents=True, exist_ok=True)
    temporary = target.with_suffix(target.suffix + ".tmp")
    temporary.write_bytes(payload)
    if temporary.read_bytes() != payload:
        raise RuntimeError("Written bytes mismatch")
    temporary.replace(target)

    delivered = target.read_bytes()
    if delivered != payload or delivered.decode("gb2312", errors="strict") != text:
        raise RuntimeError("Delivered file mismatch")

    print(f"BUILD_TIME: {datetime.now().astimezone().isoformat(timespec='seconds')}")
    print(f"SOURCE: {source.resolve()}")
    print(f"DELIVERABLE: {target.resolve()}")
    print(f"ENCODING: GB2312, no BOM; BYTES: {len(delivered)}")
    print(f"SHA256: {sha256(delivered).hexdigest()}")
    return 0


if __name__ == "__main__":
    raise SystemExit(main())
```

若已有 `.lsp` 实际并非 UTF-8，先核实其来源及真实编码，再恢复为正确的 UTF-8 开发源码。不要对不明编码的文件反复转码；示例遇到不合法 UTF-8 会明确失败。

临时文件及目标文件均位于本项目的 `output/gb2312` 下，构建只替换本工具生成的目标交付文件。写入失败时保留原始异常，不输出构建成功提示。

4. 测试中文长文本和转义格式。旧引擎可能按多字节字符串处理，不能只以 Python 侧转换往返证明 AutoLISP 中 `strlen`、`substr` 等操作正确。

旧引擎与 Unicode 引擎的字符串行为存在差异，需记录实际运行环境。Autodesk 的 [AutoLISP 更新说明](https://help.autodesk.com/cloudhelp/2026/ENU/AutoCAD-AutoLISP/files/GUID-037BF4D4-755E-4A5C-8136-80E85CCEDF3E.htm) 记载了 AutoCAD 2021 对加载及字符串函数的 Unicode 更新；[LISPSYS 说明](https://help.autodesk.com/cloudhelp/2026/CHS/AutoCAD-Core/files/GUID-1853092D-6E6D-4A06-8956-AD2C3DF203A3.htm) 说明了旧引擎及 Unicode 环境的差别。这里采用 GB2312 是用户明确的本次交付要求，不据此推断其他 CAD 版本都不能加载 UTF-8。

## 6 若正确交付编码后仍报同一错误

先确认 CAD 加载路径与已校验文件确实一致，再保留完整错误和失败阶段，定位实际接收到 `nil` 的字符串调用。用户指定速查文档第 14 节曾记录另一条 `getvar` 返回 `nil` 后被用于 `strcat` 的缺陷；该案例仅作为后续排查参考，不能据此认定本插件使用了同一变量。
